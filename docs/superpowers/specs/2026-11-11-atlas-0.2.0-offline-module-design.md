# Atlas 0.2.0: its own offline module

Status: draft for approval. Date: 2026-11-11. Repository: `nezbut/horizon-atlas`. Builds on
`specs/2026-11-08-atlas-launcher-fork-design.md` (patch queue, sync, signing), which stays in force.

## Intent and why

Until now Atlas was "upstream's launcher with offline play switched on": `patch: offline-play` set
`backend::OFFLINE_PLAY = true`, and upstream's own offline names, skins and owner-gate bypass did the rest.
Upstream commit `1e789800af` ("launcher: remove offline names; play only as an account that owns the game",
in `launcher@0.2.59`) deleted all of that, about 1750 lines of `launcher/src`: offline names, their skins and
capes (`skins.rs`, `skin_page.rs`), the developer offline switch (`dev_options.rs`, `Settings::dev_offline`),
the offline entries of the account menu and of Settings > Account, and the CLI's `account offline`,
`account forget-offline` and `account skin`. The sync to 0.2.59 now fails on `patch: offline-play`, and the
scheduled sync stops Atlas at 0.2.58 until this design ships.

The game itself still plays offline (upstream's `docs/microsoft-account.md`: "Offline play stays possible; the
launcher just doesn't offer it on its own"; "Who isn't affected: the game binary itself"):
`crates/horizon-client/src/game/launch_options.rs` takes `--name` / `HORIZON_PLAYER_NAME` and plays without a
session, and `crates/horizon-client-render/src/skins.rs` still reads `HORIZON_OFFLINE_SKIN`,
`HORIZON_OFFLINE_SKIN_MODEL` (classic|slim) and `HORIZON_OFFLINE_CAPE` for the local player.

So Atlas keeps offline play itself, in its own module, and becomes a fork with features of its own rather
than a switch on upstream's. Atlas 0.2.0 is that release (minor bump: a new Atlas feature).

## Goals

1. **Offline profiles.** Several offline names, one selected. Each name has its own skin (with the
   classic/slim model) and its own cape. Add, rename, remove, select.
2. **A "Profile" tab** in the top tab bar (beside Mods, Servers, Wardrobe...): a vertical list of the names on
   the left (selected one marked, "Add name" at the bottom, rename and remove per name), and on the right the
   selected name's skin and cape: flat previews (front of the skin, the cape), PNG pickers, the model toggle.
3. **The account menu** (the chip in the top right and its dropdown) lists the offline names, switches between
   them, and shows the selected one in the chip. Its "Manage accounts" entry opens the Profile tab.
4. **Play works offline everywhere**: the window's Play, the CLI's `play`, `modpack play`, the MCP server's play.
   The game gets the selected name, skin and cape.
5. **Atlas's accounts are its own, with room for Microsoft later.** Atlas never sees or touches the official
   launcher's Microsoft accounts or tokens: its account file and its keychain entries are its own (see "Atlas's
   own accounts"). "Who plays" in 0.2.0 is an offline name or nobody; the model has a Microsoft variant for
   later, unused until Atlas has its own client ID.
6. **No dead Microsoft sign-in.** Any "Sign in with Microsoft" button, while the build has no client ID, opens
   a small dialog: "Horizon Atlas doesn't support Microsoft sign-in yet", with OK. Settings > Account itself is
   left as upstream has it.
7. **Existing players lose nothing.** Atlas 0.1.x players' offline names, selection and skins/capes are carried
   over on the first start of 0.2.0, before upstream's code deletes them (see Migration).
8. **Installed beside the official launcher, not over it**, with shared data:
   - Windows: own app name "Horizon Atlas", own install folder, own registry keys, own Start menu and
     desktop shortcuts. The installer offers (ticked by default) to remove an old Atlas install found in the
     official launcher's folder. A launcher still running from that old folder (0.1.x self-updated to 0.2.0
     there) shows a one-time dialog pointing to the new installer.
   - Linux: own applications-menu entry, moved automatically from the old one.
   - macOS: the app is "Horizon Atlas.app" with its own bundle identifier, done at build time.
9. **The window title says "Horizon Atlas".**
10. **Every string translated**, through upstream's `tr()`, into all 86 `launcher/lang/*.json`.

## Non-goals

- Microsoft sign-in (needs Atlas's own Azure app and Mojang's approval; Horizon's client ID may not be used, per
  upstream's `docs/forking.md`).
- A 3D preview of skins and capes (ROADMAP; 0.2.0 has flat previews).
- Other players seeing your offline skin (needs a skin server; see the owner's server notes). The game applies
  the offline skin and cape to the local player only.
- Changing a Microsoft account's skin (it lives in the Mojang profile; upstream's launcher can't change it
  either). No hint about it is shown.
- A warning that renaming makes a new player in worlds (the owner chose not to show one).
- Any change to the game, and any download of Minecraft for a player who doesn't own it. Downloading from Mojang
  stays gated on an owning account exactly as upstream has it (`backend::download_for_owner` re-checks
  ownership; `patch: choose-jar` stays the way to use one's own jar).
- An in-app "move now" button on Windows (the launcher binary is also the installer, so it is possible later).

## Anti-goals (a failure even if it works)

- Re-adding upstream's removed code inside upstream's files, or any wide edit there: every changed line in an
  upstream file is a future conflict, and upstream releases launcher tags several times a day.
- Losing a player's names, skins or capes on the update.
- Touching worlds, saves, settings or anything else in the shared data folders during migration or uninstall.
- A sign-in button that pretends to work.

## Constraints

- Atlas is a patch queue on upstream's `launcher@X.Y.Z` tags, rebased by `tools/atlas_sync.py` four times a
  day. Patch commits have exact subjects (`patch: <name>`); the sync names the failing one in its issue.
  Everything else is `atlas: ...`. Commits carry no agent attribution.
- The sync auto-resolves upstream workflow files and `launcher/lang/*.json` conflicts where a patch only adds
  keys. If upstream ever adds a key with the same English text as an Atlas key, the sync stops with an issue and
  Atlas renames its key; that is accepted.
- Upstream's i18n test (`launcher/src/i18n/tests.rs`) scans every `src/**/*.rs` for literal `tr("…")` /
  `trf("…")` and requires each key in every language table, and no unused keys.
- The launcher has two looks (glass and classic: `glass_topbar`/`glass_sidebar` vs `topbar`/`sidebar`) and
  three appearances (light, dark, system). New UI must work in all of them and use the launcher's own
  components and theme tokens (e.g. `glass_ui`, `dialog_plate`, `horizon_theme`), not a new style.
- The official launcher shares the data folder (`backend::data_dir()`, e.g. `~/.local/share/horizon-launcher`,
  `%APPDATA%\horizon-launcher`) on purpose, and its current code deletes old offline data from `accounts.json`
  and `skins/` on save. Atlas's data therefore lives in its own subfolder, `atlas/`.
- The owner's rules: no commit or push without their explicit yes; files edited with the editor, not the shell;
  Python only as `uv run python`; checks: `cargo fmt --check`, `cargo clippy --release --all-targets -- -D
  warnings`, `cargo test --release --lib --bins --test owner_gate` in `launcher/`, the sync tool's tests.

## Approaches considered

1. **Own module from the old code, thin seams, several small patches** (chosen). Port upstream's 0.2.58 offline
   code (`account.rs` offline parts, `skins.rs`, `skin_page.rs`, the offline parts of `switch_page.rs` and
   `glass_account.rs`) into `launcher/src/offline/`, reshape it for the Profile tab and `atlas/` data, and hook
   it into upstream's code with a few lines per file. Costs a few hundred lines of Atlas's own code and tests;
   new files never conflict.
2. **Revert `1e789800af` inside Atlas.** Fastest way back to "as before", but ~1750 lines in upstream's most
   active files (conflicts at almost every tag), and "as before" is not this design (no Profile tab, data that
   upstream's code deletes).
3. **A wrapper outside the launcher** that starts the game with the environment. Rejected: no tab, no menu.

The owner picked 1, with the work split into four patches (below).

## Design

### The four patches

Replacing `patch: offline-play`; the other patches (`choose-jar`, `own-releases`, `own-keys`) stay as they are.

| Patch | What it holds |
|---|---|
| `patch: offline` | `launcher/src/offline/` (model, storage, migration, session, Profile tab UI, account-menu entries, CLI) and its seams; Atlas's own accounts file and keychain service; its lang keys; Atlas's adjusted owner-gate tests (`launcher/tests/owner_gate.rs`) |
| `patch: no-sign-in` | the dialog shown instead of Microsoft sign-in when the build has no client ID; its seam in `start_sign_in`; its lang keys |
| `patch: own-install` | Windows installer names, keys and folder; the "remove the old Atlas install" option; the one-time migration dialog; Linux menu entry name and its migration; their lang keys |
| `patch: branding` (extended) | the existing sidebar link, plus the window title "Horizon Atlas" |

The macOS rename is not a patch: it is done in Atlas's own `.github/workflows/atlas-release.yml`, an `atlas:`
commit. Where a patch needs a new top-level module declaration (`lib.rs`, `main.rs`), it adds its own line.

### Atlas's own accounts (`patch: offline`)

The official launcher and Atlas share the data folder, and upstream's account file `<data_dir>/accounts.json`
(Microsoft accounts and the selected one) and keychain service (`account::SERVICE`, "dev.playhorizon.launcher")
would make the official launcher's sign-ins visible in Atlas: listed first in the account menu, unrenewable
without a client ID, and removable from Atlas's Settings > Account. Instead, two one-line seams:

- `account.rs` line 1716: the accounts file is `<data_dir>/atlas/accounts.json`.
- `account.rs` line 24: `SERVICE` is Atlas's own keychain service name (for example
  "io.github.nezbut.horizon-atlas").

Effects: Atlas starts with no Microsoft accounts; the official launcher's are untouched by anything Atlas does.
Wardrobe and Shop behave as signed out (their tabs are hidden by default anyway; their sign-in button opens the
no-sign-in dialog). Settings > Account stays as upstream has it and shows an empty list with its sign-in card.
Later Microsoft support keeps its accounts in this file. The builder checks that nothing else reads the shared
`accounts.json` or the old keychain service by another path (`data_location`, which moves the whole data
folder, is expected to carry `atlas/` along).

### Model and storage (`patch: offline`)

- `<data_dir>/atlas/offline.json`: the offline names in display order, each with its skin model, and who plays.
  It is separate from `atlas/accounts.json` because upstream's code rewrites that file in its own format and
  drops fields it doesn't know. "Who plays" is one of: an offline name, a Microsoft account (by UUID, reserved
  for later, never chosen in 0.2.0), or nothing yet.
- `<data_dir>/atlas/skins/<lowercase name>.png` and `<lowercase name>.cape.png`.
- Names: 3–16 characters `[A-Za-z0-9_]`, unique case-insensitively (as upstream had). Skins: 64×64 or 64×32
  PNG; capes: 64×32 or 22×17 PNG (as upstream's `skins.rs` checked). Renaming a name moves its skin and cape.
- With no offline name at all and no Microsoft account, Play still works: the game is started offline without
  a name and uses its own kept name (`horizon-player.txt`), as the game does by itself. (My call; the chip shows
  that state as "Offline".)

### Migration from 0.1.x (`patch: offline`)

On the first start of a launcher with this patch, if `atlas/offline.json` doesn't exist yet: read, without
writing it, the shared old `<data_dir>/accounts.json` as raw JSON (`offline` names, `offline_selected`, `looks`
for the skin models), copy `skins/<name>.png` and `.cape.png` into `atlas/skins/`, and write
`atlas/offline.json`. The selected offline name becomes who plays, even if a Microsoft account was selected
there (0.2.0 has no Microsoft play). It runs once (the file's existence marks it), never changes or deletes the
old files, and a failure leaves the old data in place and is logged, not fatal. Because Atlas no longer writes
the shared `accounts.json`, only the official launcher can still drop those old fields; the copy is made at the
first start of 0.2.0, as early as possible. The CLI and the MCP server run the
same migration before they use the model.

### Who plays and the game's session (`patch: offline`)

- **The one important seam**: at the start of `account::session_for_game` (account.rs, 0.2.59 line 2240), one
  line: if Atlas's model says an offline name plays (or nobody, see above), return Atlas's offline
  `GameSession` (no session file, `env` = `HORIZON_PLAYER_NAME` and, when set, `HORIZON_OFFLINE_SKIN`,
  `HORIZON_OFFLINE_SKIN_MODEL`, `HORIZON_OFFLINE_CAPE`). Both the window (`Msg::Session` applies `env`) and
  `backend::client_as` (CLI play, modpack play, MCP play) apply that `env`, so no launch site changes. The
  builder must confirm every launch path goes through `session_for_game` or `session_for_game_as`, and route
  `session_for_game_as` (a named player for one launch, `play --account`) the same way for offline names.
- **The owner gate** (`owner_page.rs`, `asking_owner`, line 10): one condition so it doesn't cover the window
  while an offline name plays.
- **The account menu** (`switch_page.rs`: `who_plays` line 7, `play_as` line 14, `players` line 25): one line
  each, so the chip shows the offline name and the dropdown lists the offline names (keys such as
  `offline:<name>`) after the Microsoft accounts. The menu's "Manage accounts" opens the Profile tab instead of
  Settings > Account (a one-place change in `frame.rs`'s `glass_account_menu` and the classic `account_menu`).
- Upstream's `launch_for_game` auto-selects the first Microsoft account; Atlas's "who plays" therefore lives in
  `atlas/offline.json`, not in `accounts.selected` (which is empty in 0.2.0 anyway).

### The Profile tab (`patch: offline`)

- A new `Page` variant, its entry in `Page::ALL` (after Servers, before Wardrobe), and its render arm in
  `main.rs`: three small edits; the page itself is in Atlas's files (`impl Launcher` in an Atlas UI module, as
  upstream's pages do). Label "Profile", icon from the launcher's existing set. Shown in both looks.
- Left: the names, vertically, the selected one marked; "Add name" (an inline field with validation); per name
  rename and remove (remove asks for confirmation through the launcher's dialog). Right: the selected name's
  skin front and cape previews (ported from upstream's `skins::front` / `cape_front` and `skin_page.rs`), "Choose
  skin…", "Choose cape…", "Remove", and the classic/slim toggle.
- Reuse the old code and the launcher's components; no new visual style.

### CLI (`patch: offline`, my call)

Upstream's clap command enum is not touched: Atlas's commands run from a pre-hook before `cli::run()` in
`main()`. Proposed: `horizon-launcher offline list | add NAME | select NAME | rename OLD NEW | remove NAME |
skin NAME PATH [--slim] | cape NAME PATH | clear-skin NAME | clear-cape NAME`, with `--json` where upstream's
commands have it. The builder may adjust names and shape.

### No dead sign-in (`patch: no-sign-in`)

The Microsoft sign-in buttons call `Launcher::start_sign_in` (main.rs line 2023). One line at its start: if
`account::client_id()` is none, open Atlas's dialog ("Horizon Atlas doesn't support Microsoft sign-in yet", OK)
and return. "Sign in again" (`re_sign_in`) goes to `begin_sign_in` directly, but it only exists for an account
in the file, and Atlas's file has none in 0.2.0; the builder guards it the same way only if that stays cheap. The dialog is Atlas's own, built on the launcher's `dialog_plate` like upstream's dialogs. The CLI's
and MCP's sign-in keep upstream's existing refusal message.

### Installed beside the official launcher (`patch: own-install`)

- **Windows** (`installer.rs`): `APP_NAME` "Horizon Atlas", the install folder named after it (`folder_for`),
  `UNINSTALL_KEY` and `OWN_KEY` Atlas's own, shortcuts named after it. The binary name may stay. The data folder
  is unchanged (shared).
- **The old-install option.** The installer looks for an install in the official launcher's place (the old
  folder and the old registry entry). It treats it as Atlas only if that executable contains the string
  `nezbut/horizon-atlas` (Atlas's `LAUNCHER_REPO`); an official launcher there is never touched. If it is Atlas,
  the installer shows "Remove the old Horizon Atlas install (from the Horizon Launcher folder)", ticked by
  default, in both its window and its quiet mode (a flag). Removing takes the old executable, its shortcuts and
  its registry entries, never the data folder.
- **Tested on Windows.** `installer.rs` and the setup window build only on Windows, and Atlas's CI is Linux-only,
  so `atlas-ci.yml` gains a Windows job that builds the launcher and runs the installer end to end in a scratch
  profile: an old Atlas in the official launcher's folder is removed (executable, shortcuts, registry), an
  official launcher in that folder is left alone, old registry keys that now point at an official launcher
  installed elsewhere are left alone, the data folder is never touched, and a fresh install lands in Atlas's own
  folder with its own keys. `atlas-release.yml`'s Windows smoke test is updated to the new install path. The
  owner and a friend then check it by hand on real Windows machines before the release.
- **The one-time dialog.** A launcher running from the official launcher's folder (`...\Programs\Horizon
  Launcher\`) shows once: Atlas now installs on its own; to move, download the new installer, whose option
  removes this copy; worlds and settings are safe. Buttons: "Download installer" (opens the latest release's
  page), "Not now", "Don't show again" (kept in `atlas/`).
- **Linux** (`desktop.rs`): Atlas's menu entry is `horizon-atlas.desktop`, named "Horizon Atlas". When Atlas
  writes its entry (the existing repair at start), it removes an old `horizon-launcher.desktop` whose program is
  Atlas's own executable; an entry pointing at the official launcher is never touched.
- **macOS** (`atlas-release.yml`, an `atlas:` commit): the bundle is "Horizon Atlas.app" with its own
  `CFBundleIdentifier` and name, changed in the release workflow before signing (upstream's
  `packaging/macos/Info.plist` and `package.sh` are not patched). `package.sh` signs the app itself, so the
  workflow renames the bundle, edits `Info.plist`, signs again and repackages the zip and the `.dmg` after it.
  `install.sh` installs `Horizon Atlas.app`. A self-update puts the new bundle at the old bundle's own path
  (`find_app`, `replace_bundle`), so a 0.1.x player who updates keeps `Horizon.app` where it is (for a `.dmg`
  install, `/Applications/Horizon.app`, the official launcher's place). The owner accepted that: the release
  notes tell them to reinstall to get "Horizon Atlas.app". The builder confirms by reading `mac_update.rs` that
  the renamed bundle with its new identifier updates in place without breaking; if that is risky, keep the old
  identifier and change only the visible name, and say so. There is no Mac to test on: verification is by
  reading the code and by the CI build.

### Window title (`patch: branding`)

`titlebar.rs`: the window title (line 26) and the drawn title bars (Linux CSD line 86, Windows line 431) say
"Horizon Atlas"; the macOS menu names (`main.rs` 5802-5803) too. The opening "HORIZON" wordmark and the classic
sidebar's game name stay (they name the game).

### Strings

Every new user-facing string goes through `tr()` / `trf()`, with its key added to all 86 `launcher/lang/*.json`
and translated into each language (a translation pass by a light model, the Russian checked by the owner). Keys
are placed so the sync's auto-merge sees "the patch only adds keys".

## Process and release

- Work in a branch built on upstream's `launcher@0.2.59` (the first tag without offline names): the current
  Atlas stack rebased onto it, with `patch: offline-play` replaced by the four patches. `main` stays on 0.2.58
  until the swap.
- Test-driven for the model, storage, validation, migration, the session hook and the CLI; the owner-gate
  integration tests updated to Atlas's behaviour. Full checks as in Constraints, plus a run of the built
  launcher in a scratch home (`HORIZON_LAUNCHER_HOME` etc.) and a check of the game start command and its
  environment; the owner tries the window on their machine.
- The swap: rebase the branch onto the newest upstream launcher tag, run every check, then (with the owner's
  yes) `git push --force-with-lease origin <branch>:main`, release **0.2.0** by hand through `atlas-release`
  (version `0.2.0`, the upstream tag), verify the signature, close the sync issues. `next-version` continues
  from 0.2.1 by itself.
- Release notes: offline profiles; Atlas's accounts are now separate from the official launcher's (Microsoft
  sign-in isn't supported yet); Windows: Atlas now installs on its own, run the new installer to move (its option
  removes the old copy, data stays); Linux: the menu entry moves by itself; macOS: the app is now "Horizon Atlas",
  reinstall to get it under that name.
- Docs: README (Profile tab, the Windows/macOS notes), `AGENTS.md` and the `atlas-issues` skill (the patch list:
  `offline`, `choose-jar`, `own-releases`, `own-keys`, `branding`, `no-sign-in`, `own-install`), the ROADMAP.
